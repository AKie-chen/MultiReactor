# 性能测试记录（2026-09-11）

本目录是性能数据的**出处**：结果表在这里，生成它们的脚本也在这里。

## 环境与方法

- VMware 虚拟机 4 vCPU @ 3.2GHz（宿主机 Ryzen 7 7735H），本机回环（loopback）
- 服务端：`./build/multireactor --port 8080`，默认配置（4 IO + 2 worker、
  `maxQueueSize=1024`、`maxConnections=10000`），Release
- 压测端：wrk 4.0.0（闭环）、wrk2（开环定速）、`pipeline_bench.py`（自研流水线客户端）
- **每档 2 轮**，除注明外两轮差异 <2%

流水线客户端（`pipeline_bench.py`）的两点设计，用于保证数字可信：

1. 每批发 K 个请求、收齐 K 个响应，逐响应做**字节级校验**（状态行 + body 与请求
   序号一一对应）→ 吞吐数字同时是保序正确性证明；
2. 每次测试前后读服务端 `/stats`，用**服务端自己的请求计数**交叉验证客户端计数，
   排除"客户端把请求算多了"。

> 注意：第 4 节的单连接流水线数字对 VM 调度状态较敏感——同一二进制在不同 VM
> 实例上可差约 20%。跨实例比较请只比较同实例内的相对值。

## 1. 闭环基线（wrk -t4，10s）

| 配置 | 吞吐 (req/s) | P50 | P99 |
|---|---|---|---|
| `-c100` | 123,508 / 123,282 | 704 / 698 µs | 1.97 / 1.94 ms |
| `-c1000` | 126,259 / 125,942 | 6.84 / 6.81 ms | 16.95 / 16.68 ms |

> 补充（另一次 boot）：全档闭环扫描 10s × 2 轮 —— c=100 124.7k / 123.3k、
> c=500 **130.6k / 131.1k**（本机观测到的闭环峰值）、c=1000 123.7k / 122.6k、
> c=2000 120.6k / 119.7k（503 比例 0.27% / 0.30%）、c=5000 99.3k / 100.0k
> （0.32% / 0.35%）。绝对值在不同 boot 间有约 ±10% 差异（见顶部实例敏感性说明）；
> 两次 boot 的 503 比例均为 0.3% 量级，与 README 中"c≥2000 约 0.5%"同一量级。

## 2. 开环延迟扫描（wrk2 -c100，15s/档）

wrk2 按固定速率发请求、不等响应返回，消除闭环压测的 coordinated omission：
闭环只在响应回来后发下一个请求，排队时间被藏进"客户端等待"里，延迟被系统性低估。

| 目标速率 (req/s) | 实测吞吐 | P50 | P90 | P99 | P99.9 |
|---|---|---|---|---|---|
| 40,000 | 39,836 | 1.42 ms | 2.50 ms | 3.45 ms | 8.49 ms |
| 60,000 | 58,815 | 1.51 ms | 2.68 ms | 3.73 ms | 4.58 ms |
| 80,000 | 78,416 | 1.34 ms | 2.50 ms | 3.60 ms | 4.49 ms |
| 90,000 | 89,633 | 1.25 ms | 2.44 ms | 6.66 ms | 13.8 ms |
| 100,000 | 99,592 | 1.39 ms | 3.01 ms | 12.5 ms | 34.5 ms |
| 110,000 | 109,549 | 1.57 ms | 6.59 ms | 25.3 ms | 39.6 ms |
| 120,000 | 119,453 | 19.7 ms | 97.5 ms | 203 ms | 227 ms |
| 140,000 | 122,576 | 1.39 s | 2.09 s | 2.29 s | 2.39 s |
| 160,000 | 123,262 | 2.61 s | 3.17 s | 3.55 s | 3.62 s |
| 180,000 | 121,801 | 3.78 s | 4.46 s | 4.69 s | 4.76 s |

**结论**

- **拐点在 110k–120k 之间，饱和吞吐 ≈123k**，与闭环 `-c1000` 的 126k 相互印证。
- **尾部先崩**：90k 起 P99.9 从 4.5ms 恶化到 39ms，而 P50 仍在 1.2–1.6ms 纹丝不动；
  只看平均值或 P50 会完全看不到退化已经开始。
- 超过饱和点后延迟按 Little's law 线性膨胀（140k → P50 1.39s，180k → 3.78s），
  吞吐反而微降。
- 全档 **0 个 503**：`-c100` 时在途 ≤100，远低于 1024 上限，背压不可能触发。
- 与 README 旧闭环数据对比：旧数据在 140k 负载下报 P50 6.09ms；开环显示负载
  降到 80k 时真实服务延迟只有 1.34ms（P99 3.6ms）。旧表不能直接当"服务延迟"读。

## 3. 单连接流水线（请求级并行）

单条连接、批量发 K 个请求（`pipeline_bench.py 1 <K> 5`），每档 2 轮：

| 流水线深度 K | 1 | 2 | 4 | 8 | 16 | 32 | 64 | 128 | 256 | 512 | 1024 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 吞吐 (req/s) | 3,289 | 6,532 | 12,854 | 23,784 | 39,887 | 47,291 | 51,186 | 55,999 | 58,862 | 61,461 | **63,453** |
| 每请求 (µs) | 284 | 142 | 72.4 | 39.2 | 23.2 | 18.8 | 17.9 | 17.0 | 16.4 | 15.9 | **15.2** |
| 批延迟 P50 (ms) | 0.284 | 0.285 | 0.290 | 0.314 | 0.371 | 0.603 | 1.15 | 2.18 | 4.20 | 8.11 | 15.5 |

**结论**

- 单连接吞吐 **3.3k → 63.5k，19 倍**；每请求延迟 284µs → 15.2µs。这就是
  "同连接多请求独立提交 worker + seq 保序重排"带来的收益。
- **深度 ≤8 时批延迟恒定在 0.28–0.31ms**：存在约 280µs 的**固定批开销**，
  与批内请求数无关。loopback RTT 本身只有几十 µs，这个大头的合理构成是
  IO 线程 → worker 的 eventfd 唤醒 + 结果回投的跨线程 hop（也就是 README 中
  "空队列快路径（IO 线程直执行）"要砍掉的那部分）。
- 深度 ≥32 后饱和：单连接受**单个 IO 线程**的解析/提交/写回速率限制。

## 4. 连接数 × 深度矩阵（含峰值）

| 配置 | 在途上限 | 吞吐 (req/s) |
|---|---|---|
| 2 连接 × 64 | 128 | 93,208 |
| 4 连接 × 32 | 128 | 91,480 |
| 8 连接 × 16 | 128 | 60,938 |
| 16 连接 × 8 | 128 | 37,899 |
| 1 × 1024 | 1024 | 63,453 |
| 1 × 4096 | 4096 | 60,958 |
| 8 × 64 | 512 | 124,148 |
| 4 × 128 | 512 | 137,602 |
| 16 × 128 | 2048 | 182,145 |
| 64 × 32 | 2048 | 136,182 |
| 128 × 64 | 8192 | 186,748 |
| **16 × 256** | 4096 | **208,768** ← 峰值 |

**结论**

- 峰值 **208.8k req/s**，比闭环最好成绩（126k）高 **66%**，也超过了 README 中
  4 vCPU 的理论推算上限 19.7 万——说明 worker 池重构后 CPU 不再是唯一瓶颈，
  "请求级并行 + 深度流水线"能把单机吞吐再抬一档。
- 16×128 与 128×64 两种差异极大的客户端配置收敛到同一水平（182k / 187k），
  提示这是服务端/CPU 侧的天花板，而不是客户端限制。
- 前 4 行：**在途数固定 128 时，吞吐与客户端线程数单调反相关**
  （2 线程 93k → 16 线程 38k）。这是压测端（Python 16 线程 + 服务端 7 线程挤
  4 vCPU）的调度开销，不是服务端瓶颈——不要把它读成"连接多了会变慢"。

## 5. 背压（503）验证

| 负载 | 15s 内 5xx 增量 |
|---|---|
| wrk `-c1000` | 0 |
| wrk `-c3000` | **5,764（0.34%）** |
| 全部流水线配置（最高 8192 在途） | 0 |

- 与 README 中"c≥2000 出现约 0.5% 503"一致：**只有 >1024 并发非流水线连接**
  才会把线程池在途计数打满、触发 503 背压。
- 流水线负载打不满在途上限：提交由 IO 线程的读-解析驱动、worker 快速排空，
  计数器是移动目标（这也是它比非流水线多打 66% 吞吐的原因之一）。

## 6. 正确性（吞吐测试同时产出的证据）

- 所有配置 **mismatch = 0**：每个响应的 body 与请求序号逐字节比对，累计
  3000 万+ 响应（会话内服务端 `/stats` 计数 31,596,493）。
- 每次测试的**服务端计数与客户端计数完全一致**。
- `split_fuzz.py`：把 K 个流水线请求的 payload 在**每个字节位置**切开分两次发送
  （K=1/3/8，间隔 0ms/1ms），876 个切分点**全部返回 200**——跨 TCP 拆包路径无缺陷。
- 会话中唯一出现过的 5xx 就是上面刻意压出来的 5,764 个 503，其余为 0。

## 7. 一次未复现的异常（如实记录）

在本轮测试的**第一遍**（该 VM 实例当时状态异常：同机 wrk 基线比正常低约 35%、
波动大）中出现过一轮异常：

- 128×64 配置某轮：客户端报告 `mismatch=13636` + 连接被服务端关闭；
  同窗口服务端 `err_5xx` 累计增加 6,530，而日志无 ERROR 行。
- 该 `mismatch` 数字是**客户端失步后的计数**，不等于服务端真的返回了 13636 个
  坏响应，不能直接当结论。
- 重启到干净 VM 后：**31.6M 请求、16 轮同配置复跑、5 轮诊断版复跑、876 个
  逐字节拆包点，全部 0 异常**；事后所有 5xx 都能对上号（= 上面刻意压的 5,764），
  日志同样无 ERROR。
- 已排除：解析器拆包缺陷（split_fuzz 全绿）、流水线背压（各项 5xx 增量 0）、
  wrk2 高速率档（120k/140k/180k 增量均为 0。注：wrk2 输出**不含**状态码统计，
  不做增量测量会完全看不到 5xx）。
- 尚未排除：极端负载 + 环境异常时的偶发行为。静默 5xx 只有两条路径——
  505（版本不支持）/ 501（Transfer-Encoding），且二者都会 `markForClose()`
  关连接，形状与当日现象吻合，但触发条件未能复现。
- 定案手段：`pipeline_diag.py` 长时间 soak（异常批次会自动 dump 原始字节到
  `/tmp/bench/anomaly_*.bin`，并输出全状态码直方图 + 服务端 5xx 增量）。

## 8. 静态文件吞吐（2026-09-11 补充）

测试文件由 `static_bench.sh` 生成于 `/tmp/bench_static`，服务端以
`./build/multireactor --port 8080 -d /tmp/bench_static` 启动。

> 前提说明：文件都在 page cache 中、loopback 无网卡——**带宽数字是"内存拷贝
> 上限"，不代表真实网络**；小文件吞吐单轮波动 ±10%，表中 -c100 数据为 2~4 轮
> 中位，-c1000 为单轮。

### 小文件（≤64KB，LRU 内容缓存路径，wrk -t4 -c100，10s）

| 文件 | 吞吐 (req/s) | 带宽 | P50 | P99 |
|---|---|---|---|---|
| 1 KB | 67,929 | 79 MB/s | 1.42 ms | 3.9 ms |
| 4 KB | 62,770 | 257 MB/s | 1.42 ms | 3.6 ms |
| 16 KB | 48,360 | 766 MB/s | 1.94 ms | 5.0 ms |
| 64 KB | 25,160 | 1.54 GB/s | 4.01 ms | 11.5 ms |

### 大文件（>64KB，sendfile 零拷贝路径，wrk -t4 -c100，10s）

| 文件 | 吞吐 (req/s) | 带宽 | P50 | P99 |
|---|---|---|---|---|
| 128 KB | 32,045 | 3.9 GB/s | 2.42 ms | 6.1 ms |
| 300 KB | 19,330 | 5.5 GB/s | 3.59 ms | 9.3 ms |
| 1 MB | 7,056 | 6.9 GB/s | 7.80 ms | 20.4 ms |
| 4 MB | 1,921 | 7.5 GB/s | 27.9 ms | 206 ms |

### c=1000（单轮）

| 文件 | 吞吐 (req/s) | 带宽 | P50 | 文件 | 吞吐 (req/s) | 带宽 | P50 |
|---|---|---|---|---|---|---|---|
| 1 KB | 66,707 | 78 MB/s | 14.7 ms | 128 KB | 31,997 | 3.9 GB/s | 18.0 ms |
| 4 KB | 60,736 | 249 MB/s | 15.9 ms | 300 KB | 17,650 | 5.1 GB/s | 30.5 ms |
| 16 KB | 51,011 | 807 MB/s | 19.0 ms | 1 MB | 5,708 | 5.6 GB/s | 101.8 ms |
| 64 KB | 25,856 | 1.58 GB/s | 36.7 ms | 4 MB | 1,352 | 5.4 GB/s | 598 ms |

### 304 协商缓存（If-Modified-Since，无 body，-c100）

| 文件 | 吞吐 (req/s) | P50 |
|---|---|---|
| 1 KB | 73,915 | 1.21 ms |
| 64 KB | 71,800 | 1.25 ms |

### 结论

- **64KB（缓存路径）vs 128KB（sendfile）**：数据量翻倍，吞吐反而 **+27%**
  （25.2k vs 32.0k req/s），带宽 1.54 → 3.9 GB/s。按 `延迟 ≈ 基数 + 每 KB 成本`
  粗估：缓存路径 ≈ 0.35µs/KB（有效拷贝 ~2.8GB/s），sendfile ≈ 0.1µs/KB
  （~10GB/s）。**缓存路径是用户态拷贝瓶颈**——把缓存内容放进 memfd 再 sendfile
  发送，可能让 16–64KB 这一段再提一档（1KB 段是 per-request 开销主导，收益有限）
- 缓存段内**吞吐随体积下降、带宽随体积上升**：1KB 68k req/s → 64KB 25k req/s，
  说明小文件段由 per-request 开销主导（1KB 时 ≈16µs/请求），大文件段由带宽主导
- **304 路径吞吐与文件大小无关**（无 body），~72–74k req/s，比 200 路径快
  2.9 倍（64KB 时）；相对动态路由（123k）仍有差距，差距来自静态路径的
  路径解析/缓存查找/stat 等 per-request 工作
- 大文件并发并非越多越好：1MB/4MB 在 -c1000 下吞吐反而下降（4MB：1.92k → 1.35k
  req/s），P50 从 27.9ms 涨到 598ms——更多并发流争抢内存带宽与页缓存
- 与 README 旧静态数据对照：300KB sendfile 旧值 19,096 req/s，本次 19,330 ✓
  吻合；小文件旧值 74,480（另一 VM 实例、文件内容与大小未知），本次 1KB 67,929

## 9. 复现方法

```bash
./build/multireactor --port 8080 &     # 服务端（静态目录可选）
bash bench/run_bench.sh 8080 /tmp/out  # 一键复跑全部（约 8 分钟）

# 单项
python3 bench/pipeline_bench.py 1 64 5     # 单连接，深度 64，5 秒
python3 bench/pipeline_diag.py 128 64 5    # 诊断版：异常 dump + 状态码直方图
python3 bench/split_fuzz.py 8 1            # 逐字节拆包（K=8，1ms 间隔）
bash bench/static_bench.sh             # 静态文件吞吐（需服务端带 -d /tmp/bench_static 启动）
```
